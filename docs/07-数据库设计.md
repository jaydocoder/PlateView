# 数据库设计

## 1. 核心表

| 表 | 职责 |
| --- | --- |
| users | 账号、密码哈希、角色、状态和创建时间。 |
| vehicles | 车牌、归一化车牌、分类、车型、状态、版本和保留字段。 |
| resident_profiles | 村民车辆对应的人员信息。 |
| long_term_profiles | 单位、企业、干部和旅游发展车辆的通行信息。 |
| import_batches | 上传来源、状态、统计、发布人和时间。 |
| import_rows | 源行、原始值、解析值、异常和处理结果。 |
| import_effects | 已发布行的创建或更新效果及发布前快照，用于安全回滚。 |
| audit_logs | 只追加的详情查询和管理员操作记录。 |

## 2. 约束与索引

- `vehicles.normalized_plate` 在正式有效记录中唯一；导入冲突必须先进入异常流程。
- `vehicles.normalized_plate` 建立 `pg_trgm` GIN 索引，服务包含式匹配。
- 用户名唯一；禁用用户不可登录。
- `audit_logs` 不提供更新或删除业务接口。
- 所有业务表包含创建时间、更新时间、创建人、更新人和版本号。
- `import_rows` 以批次、工作表、源行和拆分序号唯一，支持同一单元格拆分多个车牌。
- `import_effects` 保存更新前车辆与分类资料快照，以及发布后的车辆版本；回滚时版本不一致即拒绝整个批次。

## 3. 乐观锁

车辆和用户更新请求必须携带当前版本号。版本不一致时后端返回冲突状态和最新版本摘要，客户端提示刷新后重新编辑。

- 管理员删除车辆通过 `vehicles.status = 'INACTIVE'` 实现，不物理删除车辆、导入效果或审计记录。
- 管理员更新账号角色或状态时不得停用或降级当前登录管理员，且数据库中必须始终至少存在一个启用的管理员账号。

## 4. 迁移

数据库结构仅通过版本化迁移脚本演进。首次启动创建扩展、表、索引和初始管理员；迁移不可依赖人工数据库编辑。
